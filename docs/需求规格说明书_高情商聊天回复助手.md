# 跨平台高情商聊天回复助手 — 需求规格说明书（SRS）

> 版本：v1.0（需求基线）　|　日期：2026-09-16　|　状态：需求规格基线（已通过评审修订，含优先级与验收准则）
> 暂定名：**情商回复助手 / EmoReply**

## 已确认关键决策（用户拍板）
1. **覆盖端**：移动端（Android / iOS）**与**桌面端（Windows / macOS）均支持（注："支持"指**功能支持**；各端交付形态不同——Android 输入法插件最完整，iOS 降级独立 App/组件，桌面输入法扩展+悬浮窗并行，见 2.3）。
2. **首期平台**：微信、钉钉；接入方式 **只读 + 复制**（不越权、不自动代发）。
3. **生成引擎**：云端大模型（质量优先，附成本/网络约束）。
4. **交付形态**：**输入法插件**为 Android 主交付面；iOS 降级独立 App/组件 + 复制，桌面输入法扩展 + 悬浮窗并行（见 2.3）。
5. **交付物**：Markdown 文档（即本文）。

## 0. 可行性结论（先给结论）

**结论：技术上可行，采用「输入法插件为交付面 + 后台消息捕获服务 + 云端大模型生成」架构，首期覆盖微信/钉钉（只读+复制）、移动+桌面双端。合规上以"只读通知、输入法注入、人工确认发送"规避封号与个保红线，可行但需持续盯平台政策。建议立项。**

| 维度 | 判定 | 关键依据 |
|------|------|----------|
| 技术可行性 | ✅ 可行 | 回复生成（云端 LLM）、意图/情感理解成熟；消息捕获用系统通知监听（合法授权能力），输入法注入为合法 IME 能力 |
| 法律/合规 | ⚠️ 可控 | 微信/钉钉 仅"读通知 + 输入法插入/复制"，不读聊天数据库、不模拟点击、不自动代发，落在授权能力内；残存平台政策解释风险 |
| 市场/商业 | ✅ 可行 | 社交焦虑+多端效率需求真实，微信输入法 AI 帮写、各类 reply 助手已验证 |
| 最高风险 | 🟠 中高 | 平台政策变动 / iOS 输入法扩展能力受限（需降级方案） |

## 1. 引言

### 1.1 目的
本文档定义「跨平台高情商聊天回复助手」的产品需求、功能边界、非功能约束与可行性结论，作为立项评审及后续设计、开发、测试的基线。

### 1.2 范围
- **面向**：个人用户，自动识别其在各 IM/社交 App 中收到的、指向自己的聊天消息，结合上下文生成"高情商"回复建议，并通过**输入法插件**（Android 主交付形态）一键插入当前输入框（或复制）；iOS 降级为独立 App/组件 + 复制，桌面以输入法扩展为主、悬浮窗并行（各端形态见 2.3）。
- **首期范围（In Scope）**：微信、钉钉的消息接入与识别（只读）、意图/情感理解、云端大模型回复生成、输入法插件交付（插入/复制）、人工确认发送。
  - **首期平台范围（新增，AI 拟定·待确认）**：以 **Android 为主交付端**；iOS 因键盘扩展无法跨 App 读内容、无法稳定读通知，**降级为实验性 / 二期**（独立 App + 复制）；桌面端以**悬浮窗 + 剪贴板先行**，完整输入法扩展（TSF/IMK）列二期。
  - **待确认决策（AI 不代裁）**：① Android 输入法内核——复用开源 IME（如 FlorisBoard / 现成拼音 SDK）裁剪，还是以悬浮窗+剪贴板为主交付面（直接决定 M1/M2 工时量级）；② iOS 是否正式移出首期；③ 生成层是否补 RAG（用户人设库 / 关系话术 / 平台礼仪向量库），若不补则建议定位改名「得体回复助手」。
- **明确不做的（Out of Scope）**：自动无确认代发、读取聊天数据库、模拟点击/越权操作、群发营销、自动养号、聊天机器人托管。

### 1.3 术语定义
- **指向当前用户**：私聊、群聊 @提及、引用/回复用户的消息，或经语义判定确需用户回应的消息。
- **高情商回复**：在准确回应的基础上，兼顾关系亲疏、对方情绪、语气得体、不冒犯、有温度。反例（不合格）：冒犯、敷衍、过度承诺、编造对方未提及事实、协助诈骗/违规。
- **输入法插件**：以系统输入法扩展（IME / Keyboard Extension / 输入法服务）为载体，在用户打字时于候选条/快捷回复区呈现建议并注入文本。
- **只读 + 复制**：仅通过系统通知监听等授权能力获取消息，回复以"插入输入框 / 复制到剪贴板"交付，全程不越权、不自动发送。

### 1.4 参考文献（评审前需核对）
- 微信、钉钉用户协议与开放平台政策；Android `NotificationListenerService`、iOS 自定义键盘扩展、Windows TSF / macOS IMK 相关文档。
- 《个人信息保护法》《数据安全法》《网络安全法》、GDPR。

## 2. 总体描述

### 2.1 产品前景
用户日常在多个 App 间切换，存在三类痛点：漏回、回错语气、社交压力大（尤其职场/客服/销售场景）。本产品作为"社交副驾"，帮用户快速理解消息、给出得体回复，降低社交负担、提升回复质量。

### 2.2 用户特征
- 重度多 App 用户、职场人、销售/运营/客服、社交焦虑人群。
- 技术门槛低，要求开箱可用、首次配置简单。

### 2.3 运行环境
> 交付形态总览：Android = 输入法插件（最完整）；iOS = 独立 App/组件 + 复制（降级）；桌面 = 输入法扩展 + 悬浮窗并行。三者均为"功能支持"，形态因平台能力而异。
- **移动端**：
  - Android 11+：自定义输入法（IME，全功能候选条）+ 通知监听服务（捕获消息），体验最完整。
  - iOS 16+：自定义键盘扩展能力受限（不能读其他 App 内容、需开启"完全访问"才能联网、无法稳定读通知），**降级为独立 App / 小组件呈现建议 + 复制到剪贴板手动粘贴**。
- **桌面端**：
  - Windows 10+ / macOS 12+：输入法扩展（TSF / IMK）+ 通知监听；桌面端可辅以全局悬浮窗/剪贴板，提升在非输入法焦点场景的可用性。

### 2.4 设计与实现约束
- **平台政策约束（最关键）**：微信/钉钉禁止第三方越权读取聊天数据库与自动化操作；本产品严格限定在"系统通知监听 + 输入法注入"，不触碰受限能力。
- **输入法插件形态约束**：iOS 键盘扩展无法跨 App 读内容，须有降级方案；桌面端完整 IME 开发成本高，需评估是否以悬浮窗+剪贴板为主。
- **隐私合规约束**：聊天内容属敏感个人信息，须本地优先、最小收集、可撤销授权。
- **算力/成本约束**：采用**云端大模型**生成，需权衡延迟、API 费用、网络可用性；敏感正文仅在使用时上云、不长期留存。
- **捕获层可插拔与降级（硬约束，新增）**：消息捕获层必须**可插拔、可整体摘除**——一旦平台政策收紧（通知能力受限）或用户关闭授权，产品须能一键降级为「纯手动粘贴的独立 App / 悬浮窗」形态，核心生成与交付能力不得强依赖捕获层。此为实现约束，非备选方案。

### 2.5 假设与依赖
- 依赖第三方云端 LLM API 完成回复生成。
- 依赖系统通知监听（Android/桌面/移动端统一为只读通知；钉钉首期同走通知监听，开放 API 仅企业/机器人场景列入二期）完成消息捕获。
- 依赖系统输入法扩展框架完成建议注入。
- 假设用户愿意为"高情商"质量付费（订阅制，含云端额度）。

### 2.6 系统架构概述（输入法插件形态）
```
[消息捕获层]  Android/桌面/移动端统一：系统通知监听（只读，不读聊天库）；钉钉开放API 仅企业/机器人场景（二期）
        │  (仅读通知/授权数据，不读聊天库)
        ▼
[理解+生成层]  本地预处理(去重/指向判定) → 云端LLM(意图/情感/关系 → 候选回复)
        │
        ▼
[交付层·输入法插件]  候选条/快捷回复区 → 用户点选 → 注入当前输入框(或复制)
        │
        ▼
[用户]  人工确认后手动发送（产品不代发）
```
- 捕获层与交付层解耦：捕获在后台服务，交付在输入法插件；二者通过本地安全通道（设备内）通信。

## 3. 功能性需求

> 标注说明：每条 FR 标注 **优先级**（MoSCoW：P0 必备 / P1 重要 / P2 增强）与 **验收准则**（可测试条件）。

### 3.1 消息接入与识别（FR-1）
- **FR-1.1【P0】** 首期支持 **微信、钉钉**；捕获方式统一为**系统通知监听（只读）**。钉钉开放 API 仅适用于企业/机器人场景，列入二期评估，不作为首期个人消息接入路径。二期再扩展企业微信/飞书/QQ/邮件等。
  - *验收*：Android 11+ 上，微信、钉钉新通知捕获成功率 ≥ 95%（通知权限已授予且"显示详情"开启时）。
- **FR-1.2【P0】** 实时监听新消息，提取字段：发送方、会话/群、内容、时间、@提及、引用关系（受通知载荷限制，部分字段可能缺失，需兜底，见 FR-1.5）。
  - *验收*："显示详情"开启时字段提取正确率 ≥ 95%；缺失字段不报错、进入兜底。**（强前置，新增）用户须开启系统通知「显示详情」，否则本条验收不适用、直接走 FR-1.5 兜底。**
- **FR-1.3【P0】** 判定"是否指向当前用户"：私聊默认 100%；群聊依据 @/回复/引用判断（**首期仅硬规则；纯语义判定降级为 P2，见 FR-1.6**）。
  - *验收*：私聊识别准确率 = 100%；群聊 @/引用识别 ≥ 98%；**首期不考核纯语义**；纯语义判定降级为 P2，见 FR-1.6（≥85% 目标移至二期）。
- **FR-1.4【P1】** 去重、聚合、过滤系统消息 / 自己发出的消息 / 非指向消息。
  - *验收*：系统消息与自己消息过滤率 = 100%；重复通知去重率 = 100%。
- **FR-1.5【P0，新增】** 内容缺失处理：当通知载荷为空（用户关闭"显示详情"）或无法识别发送方时，不强行生成；提供兜底——提示用户粘贴原文 / 仅基于标题生成泛化建议并标注"上下文有限" / 引导至企业 API 场景。
  - *验收*：空载荷场景 100% 触发兜底而非幻觉生成；用户可一键粘贴补全。
- **FR-1.6【P2，新增】** 纯语义「指向我」判定（无 @ / 无引用时的语义判断）：**列为二期增强，首期不纳入验收**——只读通知下上下文有限，纯语义判定易误判，而误打扰比漏判更伤体验。
  - *验收*：二期测试集准确率 ≥ 85%；将「无需回复」误判为「需回复」的比例 ≤ 5%。

### 3.2 意图与情感理解（FR-2）
- **FR-2.1【P1】** 消息分类：问询 / 请求 / 闲聊 / 情绪倾诉 / 通知 / 冲突 / 邀约。
  - *验收*：标注测试集上分类 F1 ≥ 0.85。
- **FR-2.2【P1】** 情感识别：对方情绪（开心/愤怒/焦虑/中性）+ 紧急度。
  - *验收*：情绪分类 F1 ≥ 0.80；紧急度与人工标注一致性 ≥ 0.85。
- **FR-2.3【P2】** 关系识别：依据**用户手动标注 / 系统通讯录权限（须授权）/ 默认"陌生"**判断亲疏（家人/好友/同事/客户/陌生）。只读通知本身不含分组信息，关系来源须显式定义，不得假设。
  - *验收*：已标注联系人关系判断准确率 = 100%；未标注默认"陌生"且不影响生成。
- **FR-2.4【P1】** 是否需回复的判定（过滤纯通知、无需回应内容）。
  - *验收*：无需回复内容误判为需回复率 ≤ 5%。

### 3.3 高情商回复生成（FR-3，云端大模型）
- **FR-3.1【P0】** 基于可用上下文 + 关系 + 情绪 + 用户人设，调用云端 LLM 生成 2–3 个候选。
  - *上下文获取策略*（解决只读约束）：① 近期通知拼装伪历史（同一会话最近 N 条）；② 用户手动粘贴补全（FR-1.5）；③ 企业/授权场景取真实历史（二期）。**质量边界**：只读通知下上下文有限，回复以"礼貌得体、不编造事实"为下限，不承诺记忆长程对话。
  - *验收*：候选生成成功率 ≥ 95%（网络正常）；默认产出 2–3 条；不出现编造对方未提及事实。
- **FR-3.2【P1】** 支持语气风格切换：正式 / 亲切 / 简短 / 幽默。
  - *验收*：四种风格可切换且风格区分可被人工辨识（抽样 ≥ 90%）。
- **FR-3.3【P1】** 附一句"为什么这样回"（解释情商点，提升可信度）。
  - *验收*：≥ 90% 候选附带可理解的解释句。
- **FR-3.4【P2】** 支持用户微调（改写、补充事实、指定长度）。
  - *验收*：微调后 ≤ 2 次交互内重新生成。
- **FR-3.5【P0】** 拒绝生成冒犯 / 欺骗 / 不当 / 违法内容（安全护栏，云端+本地双层）。
  - *验收*：红队测试集违规请求拦截率 ≥ 99%。
- **FR-3.6【P1，新增】** 离线 / 弱网降级：网络不可用或云端超时（默认 3s）时，提供本地模板兜底建议并标注"离线草稿"，不阻塞输入；恢复后自动切回云端。
  - *验收*：断网时 100% 返回模板兜底；云端恢复后自动切回；不丢失用户已输入内容。

### 3.4 回复呈现与发送（FR-4，输入法插件交付）
- **FR-4.1【P0】** 在输入法候选条 / 快捷回复区（Android 为 IME 候选条上方独立"AI 条"，不与拼音候选混排）呈现候选；移动端非输入焦点时可用通知/悬浮窗预览。iOS 经独立 App/组件呈现（见 2.3）。
  - *验收*：候选展示不影响正常输入法候选；点击展开成功率 100%。
- **FR-4.2【P0】** 用户点选后**注入当前输入框**（输入法插件原生能力）或**复制到剪贴板**；**不自动发送**，需用户最终手动发送。
  - *验收*：注入/复制成功率 ≥ 99%；全程无自动发送动作。
- **FR-4.3【P1】** 记录反馈（采纳/修改/忽略），用于个性化与优化；以**采纳率/修改率**作为"高情商"质量代理指标（目标采纳率 ≥ 40%）。反馈上云须用户授权且脱敏。
  - *验收*：反馈可被记录并可选上云；默认本地；脱敏字段不含消息正文。

### 3.5 个性化与记忆（FR-5）
- **FR-5.1【P2】** 用户人设 / 偏好配置（自称、口头禅、禁语、默认风格）；支持多端同步，冲突以"最后写入优先 + 版本号"解决。
  - *验收*：配置可保存并在多端一致；冲突解析符合策略。
- **FR-5.2【P2】** 联系人关系与历史摘要（默认本地存储，加密）。历史来源受限于只读捕获（见 FR-3.1 上下文策略），不完整时不臆造。
  - *验收*：本地加密存储可用；无历史时不生成虚构长程记忆。
- **FR-5.3【P2】** 学习用户常用语气与高频场景（基于本地反馈，可选上云）。
  - *验收*：高频场景可被识别并影响默认风格。

### 3.6 隐私与安全（FR-6）
- **FR-6.1【P0】** 消息正文仅在使用时上云（云端大模型生成所需），短期缓存 ≤ 7 天（可配置），不长期留存；元数据本地为主。
  - *验收*：正文上云仅限生成调用；超期自动清除。
- **FR-6.2【P0】** 端侧缓存加密（设备级密钥）；输入法插件与后台服务间通信限于设备内。**输入法不对外传输、不上传、不外存按键流；按键仅本地用于输入法功能。**
  - *验收*：缓存加密；无按键流外传（安全审计）。
- **FR-6.3【P1】** 一键清除全部本地数据，可关闭云同步/云生成（降级为最小本地模板兜底，非同等质量）。
  - *验收*：清除后可恢复初始态；关闭云后仅本地模板可用。
- **FR-6.4【P0，新增】** 风险消息处置：对索取钱财 / OTP / 密码、疑似诈骗或诱导违规的请求，拒绝协助生成迎合内容，并提示用户注意风险。
  - *验收*：诈骗类红队样本拒绝率 ≥ 99%；给出风险提示而非代写。

## 4. 非功能性需求（NFR）

- **性能**：候选生成 P95 < 3s（云端 LLM，含网络）；消息捕获到占位提示 < 1s、候选就绪 < 3s；输入法注入无明显卡顿。
- **安全**：传输 TLS、本地加密、最小权限；消息加密密钥不出设备（LLM API Key 仅用于调用、不留存用户输入）；输入法不对外传输/上传按键流。
- **隐私**：默认最小收集；正文仅生成时上云、可审计、可撤回；提供"纯本地模式"开关。
- **兼容性**：Android 11+ / iOS 16+ / Windows 10+ / macOS 12+；覆盖微信、钉钉近版本。
- **可用性**：首次配置 < 5 分钟（授权通知 + 启用输入法）；零学习成本；候选一眼可读。
- **可扩展性**：插件式接入新平台（新增捕获 Adapter 不改动核心与输入法交付层）。

## 6. 可行性分析（重点）

### 6.1 技术可行性 ✅
- **回复生成**：云端 LLM（GPT/Claude/国产大模型）成熟，质量可控，2–3 候选 + 风格切换可行。
- **意图/情感/关系识别**：NLP 成熟，可规则 + 模型混合；"是否指向我"语义判定为可优化项。
- **消息捕获（首期微信/钉钉）**：
  - Android：通知监听服务可合法捕获 incoming 通知（含发送方/内容摘要），**体验最佳**；（若用户关闭"显示详情"，内容可能为空，按 FR-1.5 兜底）。
  - 桌面：通知监听可行；Windows 灵活，macOS 稍受限。
  - 钉钉：首期同走系统通知监听；开放 API 仅适用于企业/机器人场景，数据完整性更高，列入二期评估。
  - iOS：无法在键盘扩展内稳定读通知 → **降级为独立 App/小组件 + 复制粘贴**。
- **输入法插件交付**：Android 自定义 IME 候选条注入成熟；Windows TSF / macOS IMK 可行但开发重，桌面可辅以悬浮窗+剪贴板。
- **难点**：① iOS 形态降级；② 通知载荷不完整导致上下文缺失；③ "指向我"判定准确率；④ 桌面端完整 IME 开发成本。
- **同类参照**：技术选型、架构、功能与体验维度的系统对比见第 9 章（GitHub 开源竞品调研）。

### 6.2 法律与合规可行性 ⚠️（可控但需守边界）
- 微信/钉钉用户协议禁止**越权读取聊天数据库**与**自动化操作**。本方案严格限定：
  - 仅用**系统通知监听**获取消息（用户显式授权的系统能力，非越权）；
  - 仅用**输入法注入/复制**交付回复（合法 IME 能力）；
  - **绝不**读取聊天数据库、模拟点击、自动代发。
- 读取通知内容涉及敏感个人信息，须：知情同意、最小收集、可撤回、可审计。
- **残存风险**：平台政策解释变动可能收紧通知读取或输入法能力 → 需预留降级（纯复制/独立 App）并持续盯政策。

### 6.3 市场与商业可行性 ✅
- 社交焦虑、多端效率需求真实；微信输入法 AI 帮写、各大输入法 AI、Replika、海外 reply 助手已验证需求。
- 商业模式：订阅制（含云端额度） + 高级人设/风格包/团队版。

### 6.4 关键风险与缓解
| 风险 | 等级 | 缓解 |
|------|------|------|
| 平台政策收紧（通知/输入法能力受限） | 🟠 中高 | 守边界（只读通知+输入法注入）；预留降级（独立App/复制）；盯政策 |
| iOS 输入法扩展能力受限 | 🟠 中 | 独立 App/小组件 + 复制粘贴降级方案 |
| 高情商"翻车"（生成不当） | 🟠 中 | 安全护栏 + 用户确认 + 风格约束 + 本地过滤 |
| 隐私泄露 | 🟠 中 | 最小收集 + 加密 + 用完即焚 + 纯本地模式开关 |
| 接入维护成本高（App 版本变动） | 🟠 中 | 插件化 Adapter；通知载荷解析做兼容层 |
| 云端大模型成本/网络 | 🟡 低中 | 订阅额度 + 缓存 + 弱网降级（本地模板） |

## 7. 总体结论
**可行，建议立项。** 采用"输入法插件为交付面 + 后台消息捕获（系统通知监听，只读）+ 云端大模型生成 + 人工确认发送"的架构。首期落地微信、钉钉（只读+复制）、移动+桌面双端，验证回复质量、留存与合规稳定性，再扩展平台与能力。

### 9.2 架构设计对比

| 项目 | 架构风格 | 模块划分 | 数据流 | 部署方式 |
|------|----------|----------|--------|----------|
| **本项目** | 捕获—生成—交付三层解耦 | 捕获层(通知监听,只读) / 理解+生成层(云端LLM) / 交付层(输入法插件) | 通知→去重&指向判定→云端LLM生成→输入法候选条(人工点选) | Android IME + 桌面输入法扩展；本地服务 |
| AstrBot | 插件化 Agent 平台 | 平台适配器 / LLM Provider / 插件 / MCP / 知识库 / WebUI | 消息事件→插件→LLM→回复（可自动/审批） | uv / Docker / 桌面 App / 1Panel / RainYun |
| AutoReply | 视觉驱动 RPA→Agent | 视觉识别 / 对象路由 / 工作记忆 / 情感分析 / 回复生成 | 截屏→VLM 提取→路由→生成→（半自动）注入 | 桌面端（Windows/Linux/macOS） |

**关键架构差异**：本项目与 wechaty 同是解决"多端消息接入"，但接入机制不同——wechaty 走**协议 Puppet（易触发封号、协议易失效）**，本项目走**系统通知监听（授权能力、合规）**；与 AutoReply 的差异在交付面——AutoReply 用视觉截屏注入（隐私/性能开销大），本项目用**输入法候选条注入（零截屏、最自然）**。

### 9.6 差异化定位与启示

- **结论**：竞品验证了"LLM + 消息回复"需求真实且技术可行；本项目在"合规形态（只读 + 输入法）+ 高情商 + 双端"上具备清晰差异化，建议立项时据此强化卖点，并以插件化 Adapter 弥补充平台覆盖短板。
