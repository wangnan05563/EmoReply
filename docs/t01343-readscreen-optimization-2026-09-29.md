# T01343 读屏功能与候选回复生成优化方案

> 状态：四项问题的核心修复已落地（m1-poc + Android），本文档为结构化方案与后续路线。
> 日期：2026-09-29 · 关联代码：`m1-poc/emoreply/preprocess.py`、`android-app/.../capture/EmoReplyReaderService.kt`、`android-app/.../ime/EmoReplyImeService.kt`、`android-app/.../store/UxSettings.kt`

## 一、问题根因分析

### 1. 右侧「我方发言」被识别成对方（方向错位）

**根因**：侧别判定阈值是**绝对像素**——`SELF_SIDE_LEFT_PX = 450px`，基于 SM-G9980（1440 宽）真机标定（对方气泡 left≈250、我方长气泡可延伸到 ~500，取中点）。该阈值隐含「屏宽=1440」假设：

- 在 **1080 宽**设备上，我方短气泡 left 可能只有 ~340-400px（< 450）→ 被误判「对方」；
- 在 **720 宽**设备上偏差翻倍，几乎全部我方消息都会判错。

这正是用户反馈「右侧我说话识别成了对方」的根因。T01149 已移除 right>1140 辅助信号（对方长气泡右缘可达 1161，辅助信号有害），但 left 阈值的绝对像素问题一直遗留。

### 2. 读屏范围固定一屏、不可调

**根因**：T01291 把多屏读屏简化为「当前屏 + 上滑 1 屏」（`extraScreens=1` 硬编码），出于「聊天默认停最下方、无需翻找」的判断。但对**需要更多上文**的场景（群聊/长讨论），用户没有手段扩大读取范围。

### 3. 上下文过多导致候选回复混杂旧话题

**根因**：`splitDialogueTurns` 把读屏到的**全部**历史发言按原始时序送入 prompt（history 无上限）。聊天窗口滚动位置越靠上、屏幕数越多，混入的已完结话题越多——LLM 会把「一小时前已聊完的事」揉进当前回复。

### 4. 消息时间戳未被利用

**现状**：读屏捕获层把纯时间/日期行（「下午 3:21」「昨天 22:31」等）当噪声**静默丢弃**。这些行恰是聊天流里唯一的「话题边界信号」——时间分隔行出现意味着前后消息有较长间隔。

## 二、优化方案（已实施 ✅ / 规划中 ⏳）

### 2.1 侧别判定改相对屏宽比例（✅ 已实施）

```kotlin
// 旧：left >= 450（绝对像素，仅适配 1440 宽）
// 新：left >= screenWidth × 0.3125（450/1440 等比迁移）
private fun isMine(left: Int, screenWidth: Int): Boolean =
    left >= screenWidth * SELF_SIDE_LEFT_RATIO   // 450f / 1440f
```

- 节点树路径与 OCR 路径统一传 `screenWidthPx()`（服务 displayMetrics，未连接回落 1440）；
- 水平坐标不受垂直裁剪影响，OCR 局部坐标系下依然成立；
- 与 T01134 折行合并改相对比例同一思路：绝对像素随分辨率/密度/字号漂移。

### 2.2 读屏范围可配置（✅ 已实施）

- `UxSettings` 新增 `read_screens`（1-3 屏，默认 1，与 T01291 口径一致）；
- 管理页（MainActivity）新增「读屏范围」滑杆（步进 1、松手落盘）；
- IME 点 👁 时 `captureMultiScreen(extraScreens = readScreens - 1)`；
- 性能权衡：每多一屏约增加「上滑动画 600ms + 截图 OCR 0.5-0.75s」，3 屏约 2.5-3s，滑杆文案已注明「越大上下文越全、耗时越长」。

### 2.3 上下文优化：时间分段 + 条数上限（✅ 已实施，双保险）

**时间分段**（回答「读屏是否把消息时间考虑进来」——结论：**有限纳入**，只作话题边界信号）：

- 捕获层：纯时间/日期行不再丢弃，转为 `时间：xxx` 标记行输出（节点树与 OCR 两条路径同构）；
- 解析层：`splitDialogueTurns`（kt）与 `split_dialogue_turns`（py）遇标记行即开启新话题段，**此前内容视为已完结话题整段丢弃**，current 只从当前段内取；
- 为什么不做更多：OCR 时间行只有「时分」粒度、无日期年份，做排序/绝对时间推理不可靠；只当边界信号最稳。

**条数上限**：history 超过 `HISTORY_LIMIT = 12` 条只保留最近 12 条（时序不变）——即使聊天流中没有时间分隔行（短时间密集聊天），也不会把超长上下文塞进 prompt。

**向后兼容**：无时间标记行时行为与旧版完全一致；`history_limit=None` 可关闭截断。

### 2.4 后续可选优化（⏳ 未实施）

| 思路 | 说明 | 评估 |
|---|---|---|
| 话题分段识别 | 侧别切换频次/语义相似度（LCS 已有）做软分段 | 收益有限，时间信号已覆盖主要场景；观察真机效果再定 |
| 时间窗口截断 | 解析时间标记的「时分」，与当前时刻比较丢弃 N 小时前内容 | OCR 无日期，跨天判断不可靠；暂不做 |
| 候选优先级排序 | 生成后按与 current 的语义相关性重排 | 属 sanitize/rank 层，另立任务 |

## 三、优先级建议

1. **P0 侧别比例修复**（✅ 本次已落地）——真 bug，方向错了候选全错；
2. **P0 时间分段 + history 上限**（✅ 本次已落地）——直接解决用户主诉的「话题混杂」；
3. **P1 读屏范围可配置**（✅ 本次已落地）——明确需求项，成本低；
4. **P2 候选相关性排序**——需真机观察 1-3 的实际效果后决定是否值得做。

## 四、待确认事项

1. **侧别比例 0.3125 的跨设备有效性**：需要在一台非 1440 宽设备上真机验证（点 👁 观察侧别标注）；当前仅 SM-G9980 标定数据。
2. **时间标记行的误保留风险**：用户消息正文恰为纯时刻（如「3:21」）会被转成标记行并触发话题截断——概率低（正文极少是纯时刻），但真机需观察；若出现，可加「时间行坐标居中」的几何条件收紧。
3. **history 上限 12 是否合适**：12 条约覆盖 5-6 轮对话；偏小可放到 16，属 UxSettings 可配置项的候选。
4. **读屏范围默认值**：维持 T01291 的 1 屏；若用户群反馈上文不足，可默认 2 屏（设置项已具备，改默认值一行）。
