# T01360 · EmoReply PC 同类产品调研与优化需求梳理（2026-09-30）

> **调研口径说明**：任务描述中「本产品定位与 GitHub 相近（代码托管）」系生成偏差——本项目 EmoReply PC 是「高情商回复助手」桌面端（Electron，悬浮窗 + 剪贴板交付 + OpenAI 兼容 LLM + 本地模板降级），与代码托管无关。本报告按「**GitHub 上的同款/同类产品**」口径调研：AI 回复生成、划词润色、桌面 AI 助手类产品的优秀实践，覆盖客户体验、功能扩展、UI、主题四个维度。若确实需要代码托管方向（GitLab/Gitea）调研，请另行说明。

## 二、客户体验提升

### 2.1 全局快捷键呼出与「二次触发恢复」
- **现状问题**：PC 端目前以悬浮窗点击为主入口，正在其他应用中打字时需要鼠标移出当前窗口，打断心流。
- **竞品做法**：uTools 全局 `Alt+Space` 呼出后失焦自动隐藏；pot 为每个功能（划词/截图/输入）独立注册全局热键；「AI快闪」支持结果隐藏后在时限内**再次按快捷键恢复原结果**。
- **建议方案**：注册全局快捷键（如 `Ctrl+Shift+E`）呼出/隐藏悬浮窗；复制文本后按快捷键直接进入生成；结果窗口支持「钉住」与「二次触发恢复」。

### 2.2 流式输出降低感知延迟
- **现状问题**：LLM 生成需整体等待，长回复时黑盒等待感明显。
- **竞品做法**：openai-translator 用 SSE 流式渲染实现「前所未有的流畅」；Chatbox、AI快闪均默认流式。
- **建议方案**：LLM 调用改流式（OpenAI 兼容接口 `stream:true`），候选区逐字渲染 + 光标动画；保留本地模板降级路径为整体返回。

### 2.3 一键回填与「替换原文」
- **现状问题**：候选产出后需手动复制→切窗口→粘贴，链路偏长。
- **竞品做法**：AI快闪结果窗提供「复制 / 替换原文 / 钉住」三动作；Grammarly 生成文本用 `Insert` 一键写回原输入框。
- **建议方案**：候选卡片提供三个动作：复制（现有）、复制并尝试自动粘贴回宿主输入框（可选开关，模拟 Ctrl+V）、重生成。移动端「撤回」经验同理反哺 PC。

### 2.4 语气透明化（生成前可见、可切换）
- **现状问题**：用户无法预知本次生成会是什么语气，只能生成后再判断。
- **竞品做法**：Grammarly tone detector 用 emoji 实时标注当前文本语气（正式/友好/急切等）。
- **建议方案**：候选 rationale 灰字区已有解释文案，升级为「语气标签」（如 😌轻松 / 💼正式 / ✂️简短），点击标签即按该语气重新生成——与移动端人设库（RAG）衔接。

### 2.5 本地历史与快速复用
- **现状问题**：生成结果用完即走，无法回看上次让 AI 润色的内容。
- **竞品做法**：pot 有独立「历史」页签；Chatbox 本地数据存储+导出 Markdown/JSON。
- **建议方案**：本地加密历史（延续零留存→「默认不存、显式开启且加密存储」的口径），支持一键复制/重发。

### 2.6 首次运行向导与连接自检
- **现状问题**：API Key 配置、模型地址填写对新手有门槛，配错只报生硬错误。
- **竞品做法**：Chatbox 首启引导选择 provider 并提供 `Test Connection`。
- **建议方案**：首启 3 步向导（Key→模型→试一句），一键测试连通性并给出镜像/代理提示。

## 三、功能扩展

### 3.1 多模型 Provider 与「多接口并行对比」
- **现状问题**：当前绑定单一 OpenAI 兼容端点，无备选。
- **竞品做法**：Chatbox 支持 OpenAI/Claude/Gemini/Ollama 多 provider；pot 支持同时勾选 3~5 个接口**并行返回、同屏对比**；AI快闪可为每个快捷按钮绑定不同模型。
- **建议方案**：支持多套模型配置；生成时可选「并行模式」同时调 2~3 个模型，候选区并排对比——天然契合本产品「多候选」形态。端侧模型预制（OnDevicePresets）作为离线档位纳入同一配置体系。

### 3.2 自定义快捷指令（风格按钮）
- **现状问题**：生成风格固定在预设人设上，无法快速增删场景按钮。
- **竞品做法**：AI快闪允许自定义按钮（名称+提示词+顺序+绑定模型）；PopClip 200+ 扩展生态。
- **建议方案**：设置页开放「快捷指令」管理：名称、提示词模板、是否置顶悬浮窗。内置「道歉/拒绝/夸赞/催办」等高情商场景包。

### 3.3 截图 OCR 取文（把移动端读屏经验带进 PC）
- **现状问题**：PC 端只能处理剪贴板里的文本，微信/QQ 等客户端内聊天记录无法结构化获取（PC 微信无控件树开放）。
- **竞品做法**：pot/openai-translator 均支持截图 OCR 后直接送翻译；本产品移动端已有 ML Kit 中文 OCR + 五层噪声过滤的成熟实现。
- **建议方案**：全局热键框选屏幕区域→OCR→作为「对方发言」上下文进入生成链路；复用 m1-poc 的 `filter_lines_in_regions` 图内文字过滤与侧别标注经验。

### 3.4 「要不要回」决策（Should-I-Reply）
- **现状问题**：所有请求都会生成回复，对「无需回复」的消息同样打扰。
- **竞品做法**：ReplyWise 的决策引擎输出 `reply_now / wait / no_reply` + 置信度 + 理由；群聊模式只响应 @。
- **建议方案**：与 SRS FR-2.4「压误判优先」一致：生成前先做一次轻量分类（可复用本地小模型/规则），判定「无需回复」时明示原因而非硬生成。

### 3.5 外部调用 HTTP 接口
- **现状问题**：无被集成能力，无法纳入个人自动化流。
- **竞品做法**：pot 提供本地 HTTP 接口（`127.0.0.1:60828/translate`），可被 SnipDo/PopClip/脚本调用。
- **建议方案**：开放 localhost HTTP 端点：`POST /generate {text, style}` 返回候选；文档化供 AutoHotkey/脚本调用。

### 3.6 个人语气学习（长期方向）
- **现状问题**：人设库（RAG）提供通用高情商模板，与「我自己平时怎么说话」仍有距离。
- **竞品做法**：Chat-Style-Bot 用微信聊天记录微调模仿口头禅；wechat-ai-assistant 规划聊天历史学习。
- **建议方案**：中期做「导入聊天记录→提取个人高频句式/口头禅→注入 RAG 语料」；端侧微调不现实，走检索增强即可。

## 四、UI 升级

### 4.1 候选卡片信息层级与 Markdown 渲染
- **现状问题**：纯文本展示，长回复排版松散，代码/列表无格式。
- **竞品做法**：Chatbox 全量 Markdown + LaTeX + 代码高亮。
- **建议方案**：候选区引入轻量 Markdown 渲染（marked/markdown-it + 高亮），卡片 hover 浮现「复制/重生成」图标按钮，默认隐藏减少视觉噪声。

### 4.2 悬浮窗锚点吸附与位置记忆
- **现状问题**：悬浮窗位置固定/漂移，遮挡内容时需手动拖。
- **竞品做法**：Grammarly widget 提供**锚点吸附**（贴近文本框/屏幕角落自动固定）并**按应用记忆位置**。
- **建议方案**：悬浮窗支持拖到四角/贴边吸附；按宿主应用进程名记忆位置；失焦自动收纳为小圆点（可关闭）。

### 4.3 加载与结果反馈
- **现状问题**：生成中只有简单等待。
- **竞品做法**：AI快闪流式显示 + 结果窗可钉住 + 超时恢复；Grammarly 建议卡带「接受/忽略/为什么」三态。
- **建议方案**：生成中显示骨架行 + 流式光标；完成时轻微弹入动画（沿用移动端 Overshoot 弹回语言）；失败态给出可操作建议（换模型/检查 Key）。

### 4.4 无障碍与多 DPI
- **现状问题**：字号固定、键盘不可达。
- **竞品做法**：Grammarly/Chatbox 均支持系统缩放；Chatbox 全键盘快捷键体系。
- **建议方案**：界面字号跟随系统 DPI 与全局缩放设置；悬浮窗与候选区支持纯键盘操作（Tab 循环 + 数字键 1/2/3 直选候选——与移动端候选区交互同构）。

## 五、主题升级

### 5.1 明暗主题跟随系统 + 手动切换
- **现状问题**：单一浅色，夜间使用刺眼。
- **竞品做法**：Chatbox 支持暗色主题与快捷切换（`Ctrl+/`）。
- **建议方案**：`prefers-color-scheme` 跟随系统 + 设置页三态（跟随/浅色/深色）；主题切换无闪烁（CSS 变量 + 启动前注入）。

### 5.2 主题令牌化与品牌一致
- **现状问题**：颜色硬编码分散，品牌色（深蓝 #08275E→青 #21AFAF）未形成体系。
- **竞品做法**：Chatbox 用 Tailwind 主题令牌管理一致性。
- **建议方案**：以 brand 规范建立 CSS 变量令牌（primary/gradient/surface/text 三层级），浅深主题共用令牌只换值；图形元素复用 `brand/` 资产。

### 5.3 自定义强调色
- **现状问题**：无个性化空间。
- **竞品做法**：uTools/Chatbox 均提供主题色选择。
- **建议方案**：提供 5~6 个品牌衍生强调色（青/蓝/紫/暖橙），悬浮窗与按钮 accent 联动；不做完整自定义主题编辑器（ROI 低）。

### 5.4 主题性能
- **现状问题**：未评估，悬浮窗常驻需低开销。
- **竞品做法**：PopClip「极致轻量，几乎不占资源」是常驻工具的生存底线。
- **建议方案**：悬浮窗隐藏时暂停渲染循环；主题样式预编译，避免运行时切换引发全量重排；监控空转 CPU 占用（目标 <1%）。

## 六、优先级汇总

### 高（P0，体验主链路）
1. 流式输出（2.2）
2. 全局快捷键呼出 + 二次触发恢复（2.1）
3. 一键回填/复制并粘贴（2.3）
4. 多模型配置 + 并行候选对比（3.1）
5. 明暗主题跟随系统（5.1）
6. 候选区 Markdown 渲染（4.1）

### 中（P1，能力扩展）
7. 语气标签切换（2.4）
8. 截图 OCR 取文上下文（3.3）
9. 「要不要回」决策（3.4）
10. 首次运行向导 + 连接自检（2.6）
11. 悬浮窗锚点吸附与位置记忆（4.2）
12. 自定义快捷指令（3.2）
13. 本地加密历史（2.5）
14. 主题令牌化（5.2）

### 低（P2，锦上添花）
15. 外部调用 HTTP 接口（3.5）
16. 自定义强调色（5.3）
17. 无障碍与键盘导航细化（4.4）
18. 个人语气学习（3.6）
19. 主题性能专项（5.4）
