# 需求再评估 — 跨平台高情商聊天回复助手（EmoReply）SRS v1.0

> 评估对象：`docs/需求规格说明书_高情商聊天回复助手.md`（v1.0 基线）
> 评估视角：技术可行性复核 + 风险再定级 + 与初版澄清的偏差修正
> 结论基调：**可行但被低估了工程与体验硬成本；建议收缩首期范围并纠正两个工程前提后再立项。**

---

## 0. 与初版可行性评估的关键偏差（先对齐）

| 项 | 初版误判（我此前给的） | SRS 实际定义 |
|----|----------------------|--------------|
| 交付面 | App 内聊天 composer 面板 / WebView 复用 | **系统级输入法插件（IME）** + 通知监听 |
| 捕获方式 | 端内采集当前会话上下文 | **系统通知监听（只读）**，不进 App 内部 |
| 覆盖范围 | 单 App（如闲鱼客服） | **跨 App**（微信/钉钉首期，系统级常驻） |
| 上下文 | 多轮上下文 + 画像 + RAG | 通知拼装伪历史 + 手动粘贴，**无 RAG** |
| 平台 | 移动 App + 桌面 WebView | Android IME / iOS 降级 App / 桌面 IME+悬浮窗 |

**处置**：初版 `app-chat-reply-tool/feasibility-design.md` 与 `prototype.html`（in-app 面板）与本 SRS 不吻合，仅在你后续改回「某 App 内置助手」形态时才有参考价值，不作为本需求主方案。

---

## 1. 总体可行性结论（修订）

仍「可行，建议立项」，但**风险等级应比 SRS 自评更高**：

- SRS 把最高风险定为 🟠 中高（平台政策 / iOS 受限）——这是对的，但**漏判了两块同样高危的项**：① Android 全键盘 IME 的自研成本；② 通知上下文贫乏与「高情商」承诺之间的质量矛盾。
- 一句话：技术路径存在、合规姿态正确（只读 + 不代发），但「输入法插件」交付面在工程与体验上有被低估的硬成本；iOS 实质不可行；核心质量被通知上下文天花板锁死。

---

## 2. 被 SRS 低估的 5 个关键风险（重点）

### 2.1 Android「全功能 IME」= 自研中文输入法（最大隐性成本）⚠️ 高危
- SRS 把 IME 当「在候选条上方加一条 AI 候选」——但要让用户把**默认输入法切到你**，你必须提供一个**完整可用的中文键盘**（拼音引擎、词库、云候选、符号、中英文切换…）。
- 否则用户每回一句就在「你的 AI 键盘」和「系统键盘」间反复切换 → 体验崩坏、留存归零。
- 从零做中文 IME 是**数月级**工程；SRS 未提「复用现成 IME 内核」，导致 **M1(4 周) + M2(8 周) 严重不足**。
- **建议**：把「基于现成开源 IME（如 FlorisBoard / 现成拼音 SDK）裁剪」列为 P0 前置决策；否则重排 M1–M3。或退一步：以「悬浮窗 + 剪贴板」为主交付面，绕开全键盘。

### 2.2 iOS 实质不可行（"功能支持"名不副实）⚠️ 中高
- iOS 自定义键盘扩展：a) 看不到对方消息（无跨 App 内容访问）；b) 通知在键盘扩展内无法稳定读取；c) 联网需「完全访问」且信任门槛高。
- 结果：iOS 只能做「独立 App 手动粘贴」——与「社交副驾、零切换」核心价值相悖，等于降级成 message-assistant-ai 类纯手动工具。
- **建议**：iOS 从「首期功能支持」改为「明确二期/实验性」，不对外承诺双端一致体验，不在路线图给 P0 权重。

### 2.3 通知上下文贫乏 vs 「高情商」承诺（核心质量矛盾）⚠️ 高危
- 「高情商」依赖关系亲疏 + 对方情绪 + 语境；但合规捕获只有**通知摘要**（且依赖用户开启「显示详情」），多轮语境是「同会话最近 N 条通知拼装」的伪历史，群消息常被截断。
- 直接撞墙：上下文越贫，越易「编造/泛化/翻车」。FR-3.1 已设「不编造事实」下限，但**情商质量上限被通知天花板锁死**。
- **建议**：质量预期从「高情商」务实降为「得体、安全、不冷场」；把「显示详情开启」列为验收强前置；Phase 2 用企业/授权场景取真实历史来兑现高阶情商。

### 2.4 「指向我」纯语义判定 85% 偏乐观 ⚠️ 中
- 仅用通知内容（无会话上下文）做纯语义「是否找我」判定，且须避免误打断。真实群聊噪声下 85% 难达；**误判（不需要回的弹出来）比漏判更伤体验**。
- **建议**：首期收紧为「@/引用/私聊」硬规则（≥98% 可达），纯语义判定降为 P2 实验，避免打扰。

### 2.5 平台政策灰区 + 微信通知内容加密趋势 ⚠️ 中高
- 即便「只读通知 + IME 注入」自认合规，微信/钉钉 TOS 仍可能认定违规；且微信已在部分场景将通知显示为「你收到一条消息」而需「显示详情」，群消息仍常截断。
- 政策收紧会直接废掉捕获层。SRS 已有降级预案（好），但应把「**捕获层可插拔、能一键降级为纯手动粘贴 App**」作为架构硬约束而非备选。

## 3. SRS 与初版澄清的偏差：RAG 去哪了？

- 初版澄清时你选了「多轮上下文 + 画像 + **RAG**」，但 SRS 的 FR-3.1 上下文策略只有「通知拼装伪历史 / 手动粘贴 / 企业授权历史」，**无 RAG / 知识库**。
- 影响：没有业务知识库，「高情商」只能靠通用 LLM 人设 + 风格切换，难以体现差异化与可控性。
- **建议（二选一）**：
  1. 若坚持「高情商」差异化 → 在生成层补 RAG（用户人设库 / 关系话术模板 / 平台礼仪规则向量库）；
  2. 否则删掉「RAG」承诺，定位改名为「得体回复助手」。

## 4. 其他可改进点（建议纳入修订）

- **FR-6.2 按键流（信任命门）**：自定义 IME 天然拿到全部按键流，必须满足「不上传、本地仅用于输入」并过独立安全审计——建议单列安全审计清单（含第三方审计/渗透）。
- **成本与额度**：每消息云端 LLM + 订阅，需明确额度与超量降级；弱网模板（FR-3.6）兜底文案要可接受，别让「离线草稿」显得敷衍。
- **验收 KPI**：采纳率 ≥40% 作「高情商」代理指标偏弱；建议补「二次修改率 / 忽略率 / 被平台风控触发次数」。
- **首次配置**：IME + 通知双权限申请，「<5 分钟」偏理想，建议实测引导流程并配视频/动图指引；默认键盘切换是最大转化漏斗。

---

## 5. 修订后的 Go / No-Go 建议

**Go，但必须满足以下收缩与纠正：**

1. **首期只做 Android**，且**基于现成开源 IME 内核**做「全键盘 + AI 条」；不做 iOS 无缝、不做桌面 IME（桌面改悬浮窗 + 剪贴板先行，见 M2）。
2. **质量承诺务实化**：从「高情商」调整为「得体安全不冷场」，强依赖「显示详情」前置；Phase 2 用企业/授权历史兑现高阶情商。
3. **RAG 二选一**：补进生成层（保留差异化）或从定位中去掉。

**不纠正的风险**：若坚持「自研全键盘 IME + iOS 无缝 + 双端一致」，工程量与体验风险会显著超 SRS 排期（M1–M3 需重排）。
