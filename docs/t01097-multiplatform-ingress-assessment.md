# T01097 · 多平台消息接入扩展评估（企业微信 / 飞书 / QQ / 钉钉开放 API）

> 来源：T01055 M4二期扩展（SRS FR-1.1「二期再扩展企业微信/飞书/QQ/邮件等」）
> 依据：各平台官方开发者文档检索核实（2026-09-26，来源链接见文末）
> 结论先行：**四平台的官方 API 均无法满足「用户个人消息只读接入」——官方能力只覆盖「与机器人相关的消息」，全量消息读取均为企业级付费/管控能力，个人开发者不可达。通用合规路径仍为系统通知监听。**

---

## 一、逐平台评估

### 1.1 企业微信（WeCom）

| 维度 | 结论 |
|------|------|
| 官方读取路径 | 会话存档（会话内容获取接口 `sync_msg`） |
| 授权模型 | 企业管理后台开通会话存档 + 2024-12-31 起**强制「数据与智能专区」权限**（服务商需专区接入，企业一键授权）+ 员工告知同意（外部联系人需其同意） |
| 成本 | 企业级付费能力（专区按接口 × 时长计费）+ 历史付费迁移门槛 |
| 个人开发者可达性 | ❌ 不可达——必须有企业主体、超级管理员、资质材料与合规确认函；只可获取授权范围内员工相关会话，且仅 5 天内记录 |
| 对个人用户消息的覆盖 | ❌ 与普通微信个人聊天无关（个人微信消息不经过企微会话存档） |

**判定：不可行**。个人用户与微信好友的聊天不产生企微会话存档数据；企业级路径与产品"个人社交副驾"定位错位。

### 1.2 飞书（Feishu）

| 维度 | 结论 |
|------|------|
| 官方读取路径 | ① 机器人事件订阅 `im.message.receive_v1`（WebSocket 长连接）；② `im:message` 全量读取（需企业管理员授权范围） |
| 授权模型 | 个人版飞书即可创建"企业自建应用"+ 添加机器人能力；`im:message.p2p_msg:readonly`（单聊）、`im:message.group_at_msg:readonly`（群@）需 bot 能力；全量消息读取需企业管理员开通 |
| 个人开发者可达性 | ⚠️ **机器人对话模式可达**：用户与机器人单聊、群里 @机器人，个人开发者自助配置即可跑通 |
| 对个人用户消息的覆盖 | ❌ 只能收到"发给我这个 bot"的消息；群内他人之间的消息收不到（除非企业管理员授予全量权限并发布应用版本） |

**判定：机器人模式可行但语义错位**——能做「EmoReply 机器人助手」（用户主动把消息转发/复制给 bot 请求建议），**不能替代个人消息捕获**。作为产品延伸（bot 形态）可列观察项，不解决 FR-1 需求。

### 1.3 QQ

| 维度 | 结论 |
|------|------|
| 官方读取路径 | QQ 机器人开放平台 OpenAPI v2：`C2C_MESSAGE_CREATE`（私聊）、`GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE`（群聊，后者需私域权限） |
| 授权模型 | 个人开发者可注册（身份证认证），bot 需平台审核；企业认证获更高配额 |
| 平台限制（实测口径） | 群聊默认仅 @机器人 触发；主动消息强管控（用户可关、频控 30-60 qpm）；**URL 链接不能发送**；消息格式受限 |
| 个人开发者可达性 | ⚠️ **机器人对话模式可达**（同飞书，限制更多） |
| 对个人用户消息的覆盖 | ❌ 仅 bot 相关消息；非 @ 的群消息收不到（私域权限需企业资质审批） |

**判定：同飞书，机器人模式可行但语义错位；平台限制（禁 URL、被动消息 5 分钟窗口）进一步压缩价值。不可行。**

### 1.4 钉钉（DingTalk）

| 维度 | 结论 |
|------|------|
| 官方读取路径 | ① 企业机器人接收消息（仅 @机器人 / 人与机器人单聊）；② 「钉钉客联」事件订阅"发送消息事件"可收**全部消息记录** |
| 授权模型 | ① 企业内部应用 + 管理员授权；② 客联事件订阅属企业管控场景（文档明确"建议在企业开发者指导下完成"），面向企业客服/合规场景 |
| 个人开发者可达性 | ⚠️ 机器人 @模式可达；❌ 全量消息订阅不可达（客联为企业场景） |
| 对个人用户消息的覆盖 | ❌ 普通个人群（非企业内部群）无任何官方读取 API；CSDN 传闻的"群会话消息读取权限"仅限企业自建应用 + 管理员授权 + 指定群组 |

**判定：同上，机器人模式可达但语义错位；SRS 2.5 已有的结论（钉钉开放 API 仅企业/机器人场景）经核实维持不变。**

## 二、横向对照

| 平台 | 个人可达路径 | 收到什么 | 全量读取 | 判定 |
|------|-------------|---------|---------|------|
| 企业微信 | 无 | — | 企业付费专区 | ❌ 不可行 |
| 飞书 | 自建应用机器人 | 单聊 bot / 群 @bot | 需企业管理员授权 | ⚠️ 仅 bot 模式 |
| QQ | 开放平台机器人 | 单聊 bot / 群 @bot | 私域权限需企业 | ⚠️ 仅 bot 模式 |
| 钉钉 | 企业机器人 | 单聊 bot / 群 @bot | 客联企业场景 | ⚠️ 仅 bot 模式 |
| **系统通知监听**（现状） | 用户授权即可 | **用户本人的全部通知** | —（只读通知） | ✅ 唯一通用路径 |

## 三、结论与建议

1. **多平台个人消息接入的通用合规路径维持现状**：Android 端系统通知监听（SRS FR-1.1 设计正确），无需因"二期平台扩展"引入新接入层。
2. **四平台官方 API 与产品语义错位的根因**：官方 API 的消息读取主体是"应用/机器人"，而产品需要以"用户本人"视角收消息——只有系统通知监听是"用户本人授权"的只读通道。
3. **可做的延伸（建议另立观察单，不排期）**：
   - 飞书/QQ/钉钉机器人模式：用户把收到的消息转发给 bot 请求高情商建议（产品从"副驾"延伸为"助手"），飞书个人版跑通成本最低；
   - 邮件接入（T01098）：IMAP/OAuth 是**用户自己的账号**，语义与产品匹配，是二期扩展里唯一路径匹配的平台。
4. **明确不做**：任何 UI 自动化/无障碍服务读取聊天内容的方案（违反 SRS 合规红线 2.4"不模拟点击/不越权"，且各平台用户协议禁止）。
