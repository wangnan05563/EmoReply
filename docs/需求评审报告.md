## 三、关键矛盾点详述

### 3.1 交付形态 vs 全端支持（F1）
决策声称"移动+桌面都支持"且"交付形态=输入法插件"，但技术章节承认 iOS 只能降级为独立 App/组件、桌面 M2 先以悬浮窗+剪贴板交付。本质是：**输入法插件是 Android 上的完整形态，iOS/桌面是功能等价但形态不同的降级/并行方案**。当前文档把"形态"和"功能"混为一谈，会在开发排期与验收时造成歧义。必须在范围与决策记录中把"支持"显式限定为"功能支持"，并标注各端实际交付形态。

### 3.2 只读通知 vs 上下文高情商（F3）
本产品最大卖点是"高情商"，而高情商依赖上下文（对方前文、关系、语气）。但"只读+不读聊天库"意味着捕获层只拿到单条通知，没有会话历史。FR-3.1/FR-5.2 的"上下文/历史摘要"在当前架构下无数据来源。这是**产品价值与合规约束之间的核心张力**，必须正面回答：上下文从哪里来、质量下限是什么。否则"高情商"会退化为"通用礼貌话术"，差异化被削弱。

### 3.3 钉钉开放 API 适用性（F2）
钉钉开放平台（H5微应用/机器人/事件订阅）面向**企业内应用与机器人会话**，不能读取普通用户与其他人的个人 1:1 私聊。把"钉钉授权场景走开放 API"作为首期个人消息接入路径是事实错误，会误导技术方案。首期应与微信一致走通知监听；开放 API 仅在企业/机器人场景成立，留作二期。

### 3.4 IME 安全措辞（F5）
输入法必须处理用户全部按键流才能提供候选与输入——这是 IME 的工作本性。写"不采集无关按键"在技术与合规上都不严谨，易被安全审计质疑。正确表述应聚焦"不上传、不留存、不外传按键流"。
