# 钉钉「AI 灵动回复」生成质量保证机制分析与借鉴

> 任务：T01345 ｜ 日期：2026-09-29 ｜ 类型：竞品分析 + 落地建议
> 结论先行：**钉钉在"生成质量保证"上真正做对的是"用多样性 + 关系感知对冲单条生成的不确定性，并把最后一道质量关留给人类"**；
> 这不是模型能力问题，而是产品设计问题，其中 4 条可低成本迁移到本项目。

---

## 一、钉钉做了什么（公开可核验事实）

来源：钉钉官方站点 8.1.10 发布说明、新浪科技/新浪财经 2025-12-11 报道、风尚咨询等；平台级工程原则来自钉钉 AI 助理平台公开技术实践分享。

### 功能形态

| 项 | 事实 |
|---|---|
| 版本/入口 | 钉钉 8.1.10 上线；入口在**聊天输入框右侧图标**，一键触发；PC 端与手机端均已支持 |
| 上下文 | 基于**当前聊天对话的上下文** |
| 关键前置识别 | **识别用户与对话对象的身份及组织关系**（上下级 / 同事 / 客户） |
| 产出 | 一次生成 **4-6 条**回复建议，覆盖**简洁、专业、主动确认、轻松活泼**等多种语言风格与语气口吻 |
| 场景化倾向 | 上下级沟通 → 优先正式/简洁/主动确认型；销售咨询/客服 → 更侧重礼貌询问、耐心解答 |
| 棘手情境 | 能识别"同事想蹭车""挖坑式聊天"等微妙尴尬氛围并给出高情商应对 |
| 交付方式 | 用户**可在此基础上二次编辑后发送**（保留个性化表达） |
| 个性化 | 持续综合学习用户与当前联系人的历史对话，"越用越好用" |

### 质量保证的六个机制（这才是值得抄的部分）

1. **关系感知决定语气分布**——语气不是用户每次手调的参数，而是由"对方是谁"推导出的默认值。
2. **多样性覆盖而非单一最优**——一次给 4-6 条跨风格候选，用"让用户挑"来对冲"模型单条不稳定"。
3. **人机分工明确**——AI 只出草稿，最后一道质量关（是否发送、是否改词）永远在人手里。
4. **情境分类层**——在生成前先判断"这是什么性质的对话"（任务分派 / 客户咨询 / 尴尬请求），再决定策略。
5. **个性化反馈闭环**——持续学习用户与该联系人的历史，越用越贴合。
6. **灰度 + 数据驱动的功能准入**——该功能最初是内部"玩一下"的小创意、起初不被看好，
   但在灰度中发现**显著带动聊天对话量增长**后才正式上线；功能去留由数据而非主观判断决定。

### 平台级工程原则（可迁移的方法论）

- **质量为王，不稳定即零**：不稳定的能力对用户体验是毁灭性的，**规模必须让步于质量**。
- **大量工程，少量算法**：只在 LLM 具备稳定优势的推理环节引入算法，精确计算与业务校验全部用工程兜底。
- **快慢思考结合**：高准确要求场景用"慢思考"（多步推理验证），简单查询走"快思考"直通。
- **全链路可干预**：在推理、执行、反馈各环节都能插入硬性规则，避免 LLM 陷入死循环或偏离业务约束。
- **自动评估闭环**（DeepResearch 的 DingAutoEvaluator）：对产出做多维度质检（数据准确性、逻辑连贯性、
  工具使用规范），发现问题的案例自动回流训练流程，形成"生成 → 评估 → 优化"闭环。

## 二、与本项目（EmoReply）现状逐条对照

| 钉钉机制 | 本项目现状 | 差距 |
|---|---|---|
| 关系感知决定语气 | 已有 `PersonaStore`（含 `relation` 关系字段、`defaultStyle`），但 **tone 是全局单值滑杆**（`UxSettings.tone`，0-100，默认 50），**每次需手调、不随对端关系自动变** | ⚠️ 有数据没用上 |
| 一次给多风格 4-6 条 | 候选由 LLM 输出经 `expandCandidates` 解析，**条数不固定**；风格受 `STYLES`（正式/亲切/简短/幽默）单值 + `toneHint(tone)` 单档位约束 → **一次出的多条基本同语气** | ⚠️ 缺"跨风格并行" |
| 二次编辑后发送 | 候选点选后**注入输入框**，用户可直接编辑再发送（T01127 起） | ✅ 已对齐 |
| 棘手情境识别 | 有 `Guardrail.screenIncoming` / `screenCandidate`（验证码、密码、银行卡、身份证等敏感信息识别与拦截） | ✅ 我们的护栏比钉钉公开口径**更硬**（输入侧敏感信息防护钉钉未提及） |
| 个性化反馈闭环 | 有 `FeedbackStore`（记录采纳/忽略，`adoptionRate()` 统计采纳率），但**只统计、不反作用于生成** | ⚠️ 断环 |
| 灰度 + 数据准入 | 有 `UxSettings` 开关体系（表情/暗色/精简/读屏范围等），新能力可默认 off | 🟡 具备条件，未形成机制 |
| 自动评估回流训练 | 无（我们用三方 LLM API，**不具备训练闭环**） | ❌ 不适用 |
| 快慢思考 | 无；IME 场景对延迟极敏感 | ❌ 不应照搬（见第四节） |
| 候选可解释性 | 我们有 `rationale` 理由列（T01291 恢复），每条候选附一句理由 | ✅ **钉钉没有**（我方差异化优势） |

## 三、可借鉴的优化项（按 ROI 排序）

### P0-1　关系感知 → 语气默认档位（低成本、高感知）

**做什么**：把 `UxSettings.tone` 从"全局固定值"升级为"可自动"。新增自动档（如 `tone = -1` 表示 AUTO），
生成时按 `PersonaStore` 当前联系人/群的 `relation` 映射默认 tone：

- 上级 / 客户 / 外部 → 偏理性克制（约 30-40）：措辞精简、避免感叹与过度承诺
- 同事 / 平级 → 中性自然（约 55-60）
- 好友 / 家人 → 偏活泼（约 70-80）

用户仍可手动覆盖，手动后记住该联系人偏好（写入 persona）。

**落点**：`UxSettings.tone` 增加 AUTO 常量；`EmoReplyImeService.runManualPipeline` 取 tone 时，
若为 AUTO 则查 `PersonaStore` 的 `relation` 映射；`Compose.toneHint` 复用现有 5 档描述，无需改提示词结构。

**为什么值得**：这是钉钉"高情商"感知的最主要来源，而我们**数据已经在库里了**（`relation` 字段），
只差一层映射——投入极小、体验差异极大。

### P0-2　多风格并行生成（对冲单条不确定性）

**做什么**：新增"多风格模式"——一次请求内把 tone 展开成 2-3 个档位（如 40 / 60 / 80），
每个档位出 1-2 条，最终候选集天然跨语气分布，用户挑一条即可。

**落点**：`buildPrompt` 支持传入 tone 区间；`ReplyPipeline` 多档并发（或单次请求内要求"分别用三种语气各给一条"，
后者成本更低、延迟更短，优先选这个）；开关放 `UxSettings`，默认关（老行为不变）。

**代价**：token 与延迟上升。**必须先评估 IME 场景的延迟容忍度**——建议先做单请求多语气（不增加 RTT），
只有在实测延迟可接受时才考虑并发多请求。

### P1-1　棘手情境标签（对齐"挖坑式聊天"能力）

**做什么**：在既有的 `Guardrail` 之上加一层**情境分类**，识别"请求类可能构成过度承诺 / 蹭车 / 借钱 / 甩锅"
等棘手语境，命中时在提示词追加一条约束："给出既不得罪也不做出承诺的回复，必要时提供替代方案"。

**落点**：新增 `core/Situation.kt`（规则优先，与 `Guardrail` 同风格：正则 + 关键词，可解释、可单测）；
命中标签注入 `buildPrompt`；m1-poc 先行加 pytest。

### P1-2　把采纳率闭环接回生成（断开的一环）

**做什么**：`FeedbackStore.adoptionRate()` 已经能算出"哪类回复用户不采纳"。把它变成动作：

- 按 `relation × tone × style` 维度统计采纳率；
- 某组合长期低于阈值（如 <30%）→ 自动下调该联系人默认 tone 一档，或在该场景**优先返回 `TemplateStore` 模板**
  （模板是人工校准过的，稳定性远高于模型生成，直接对应钉钉"质量为王、不稳定即零"）。

**为什么可行**：我们无法像 DingAutoEvaluator 那样回流训练，但可以**在推理侧做路由**——
低分场景不去赌模型，改走确定性更高的模板。这是"大量工程、少量算法"原则的直接落地。

### P2　灰度数据准入机制

新能力（如多风格模式、情境标签）默认 off，通过 `UxSettings` 放开，`FeedbackStore` 观测采纳率与延迟，
达标后才转正为默认。避免"自认为好用"的功能污染主链路。

## 四、不建议照搬的部分（及理由）

| 钉钉做法 | 不照搬的理由 |
|---|---|
| DingAutoEvaluator 式"问题案例自动回流训练" | 我们调用三方 LLM API，**没有训练闭环**；等价替代是 P1-2 的"推理侧路由到模板" |
| 快慢思考（慢思考 = 多步推理验证） | IME 场景延迟是第一约束——用户在键盘前等候选，多步推理的秒级开销不可接受。正确做法是**保持快，用多候选对冲**（P0-2），而非变慢 |
| 委托权限交集 / 影子账号体系 | 与企业组织架构强绑定，IM 回复助手无代操作业务系统，不适用 |
| 一次固定出 4-6 条 | 条数应由上下文复杂度决定，硬定 4-6 会在简单场景产生冗余（我们的 `expandCandidates` 动态解析更合理） |

## 五、本项目的差异化优势（应加强而非放弃）

1. **跨 App 读屏上下文**：钉钉只能基于自己平台内的消息；我们通过无障碍读屏可在任意聊天 App 上工作
   （含侧别判定、图片文字过滤、话题分段等已落地能力）。
2. **候选理由列（rationale）**：每条候选附一句生成理由，可解释、便于用户判断——钉钉公开口径中未见此设计。
3. **输入侧敏感护栏**：`Guardrail.screenIncoming` 拦截验证码/密码/银行卡等，钉钉公开资料未提及 IM 场景的同类防护。
4. **零留存 + 端侧可选**：本地加密存储、端侧离线模型（FR-8.1）与"密钥不出设备"口径，对隐私敏感用户是硬优势。

## 六、待确认事项

1. **延迟预算**：多风格并行（P0-2）前需实测当前云端生成 P50/P95 延迟；若已接近用户容忍上限，
   优先做单请求多语气而非并发多请求。
2. **relation 数据来源**：`PersonaStore.relation` 目前由用户手动维护还是自动推断？若需手填，
   P0-1 的覆盖率会打折扣，需先评估是否要补"自动关系推断"（可从称呼、群类型、历史语气推断，但需谨慎，误判代价高）。
3. **模板库质量**：P1-2 依赖 `TemplateStore` 的模板质量与覆盖面；若模板质量不足，降级反而会更差，需先盘点。
