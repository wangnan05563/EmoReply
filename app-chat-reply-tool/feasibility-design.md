# App 用户侧聊天消息助手 — 可行性评估与技术设计

> 范围确认（来自需求澄清）：
> - **形态**：用户侧聊天消息助手 —— 帮助 App 普通用户（如闲鱼卖家/买家）起草、润色、发送前优化将要发给对方（交易对象）的消息。
> - **平台**：移动端 App + 桌面应用（双端）。
> - **能力**：多轮上下文 + 用户画像 + RAG 检索增强生成。

---

## 1. 可行性结论

**整体可行性：高（8/10）。可以立项，按 MVP 节奏推进。**

| 维度 | 评级 | 说明 |
|------|------|------|
| LLM 生成回复 | ✅ 成熟 | 模型 API（SiliconFlow/Qwen、DeepSeek 等）已验证，流式输出稳定。 |
| 多轮上下文注入 | ✅ 可行 | 端侧采集最近 N 轮对话 + 商品/订单上下文，脱敏后上报。 |
| 用户画像 | ✅ 可行 | 角色（卖家/买家）+ 历史采纳话术风格向量，用户可控开关。 |
| RAG 知识检索 | ✅ 可行 | FAQ / 商品库 / 话术模板 / 平台规则向量库，你已有 news 知识库问答可复用。 |
| 跨平台一致体验 | ⚠️ 有挑战 | 移动 + 桌面双端，需统一设计系统 + WebView 复用策略。 |
| 隐私合规 | ⚠️ 需前置 | 上下文脱敏、不出域、用户可清除，上线前需法务/安全评审。 |
| 成本与延迟 | ⚠️ 需工程 | 移动端走服务端推理，流式 + 预检索缓解延迟。 |

**核心判断**：难点不在 LLM 本身，而在「上下文/画像采集的隐私合规」「RAG 业务语料质量」「双端一致体验」。这三块应作为设计重点。

---

## 2. 产品形态与设计语言

- **嵌入位置**：聊天输入框上方/侧边的「AI 帮写」入口，不喧宾夺主（轻白极简风，复用既定视觉：bg `#ffffff` / text `#111111` / 次级 `#777777`，无机器人图标）。
- **交互闭环**：用户点击「AI 帮写」→ 面板展示上下文概览 + RAG 参考 + 1~3 条候选回复 → 采纳 / 内联编辑 / 换一批 → 确认发送。
- **权责边界**：AI 仅生成草稿，**最终内容由用户确认后发送**，平台不承担话术承诺责任（需在 UI 明确免责提示）。

---

## 3. 技术架构

### 3.1 端（移动 + 桌面，共享 Web 组件）
推荐策略：**原生承载核心聊天，AI 助手面板用 WebView 复用同一套 React H5 组件** —— 一次开发、双端复用，契合你现有前端栈与轻白设计语言。

- **移动端**：React Native / Flutter 原生壳，AI 面板用内嵌 WebView 加载同一套 H5 组件。若原生薄弱，可全量 H5 + Capacitor 壳进一步降本。
- **桌面端**：Electron 或 WebView2 封装同一套 Web 组件。
- 共享：设计系统（轻白极简）、候选卡片组件、采纳/编辑/换一批交互、埋点 SDK。

### 3.2 服务端（双端共享）
```
[端] 采集上下文(脱敏) ──► [会话上下文服务] ─┐
[用户画像服务] ───────────────────────────┤
[RAG 检索服务] ───────────────────────────┼─► [回复生成编排层]
                                          │    (prompt 组装 + LLM + 安全护栏)
                                          ┘              │
                                                  [候选回复 1~3 条]
                                                          │
                                              [安全护栏过滤] ──► [端渲染]
```

- **会话上下文服务**：采集当前对话最近 N 轮、商品/订单 ID（仅 ID，不直接带隐私字段）。
- **用户画像服务**：角色标签 + 风格向量（正式/亲切/简洁）+ 用户可控开关。
- **RAG 检索服务**：业务语料向量库（chromadb / pgvector），语义检索 + 关键词兜底 + 重排。
- **回复生成编排层**（参考 karpathy-wiki harness 的 LLM + 工具循环 + hooks 模式）：
  `system(角色约束) + 画像(风格) + 检索片段(事实/话术参考) + 多轮上下文(对话) → LLM → 护栏 → 候选`
- **反馈/学习**：采纳率、用户编辑 diff 回流，用于话术模板与检索优化。

---

## 4. 一次「AI 帮写」数据流

1. 用户点击「AI 帮写」（或在输入时触发）。
2. 端侧采集：最近 N 轮对话 + 商品/订单上下文 + 画像标签，**脱敏**后上报。
3. 服务端：画像注入 → RAG 检索 top-k → prompt 编排。
4. LLM **流式**生成 1~3 条候选。
5. 安全护栏过滤（敏感词 / 诈骗话术 / 虚假承诺 / 未成年人保护）。
6. 端渲染候选卡片；用户采纳 / 编辑 / 换一批。
7. 反馈埋点（采纳、编辑、忽略）。

> 延迟优化：用户打字时即可**并行预检索**，点击「帮写」时直接进生成阶段。

---

## 5. RAG 设计

- **语料来源**：平台规则 FAQ、商品/服务知识库、高频话术模板、历史优质对话（脱敏）。
- **处理**：切分 → embedding（本地或云端）→ 向量库。
- **检索**：语义检索 + 关键词兜底 + 重排（rerank）。
- **关键约束**：用户侧助手要避免「替用户承诺」，检索内容仅作**风格 / 事实参考**，不生成确定性承诺话术。需建立评测集衡量召回质量（效果下限由 RAG 决定）。

---

## 6. 用户画像与上下文模型

- **角色**：seller / buyer（决定语气与立场）。
- **风格**：历史采纳话术的风格向量（正式 / 亲切 / 简洁）。
- **约束**：禁止泄露隐私字段；画像**用户可控开关**，可一键清除。

---

## 7. 安全与合规（用户侧尤其重要）

- **护栏层**：敏感词、诈骗/引流话术识别、避免虚假承诺、未成年人保护。
- **免责声明**：AI 生成内容为草稿，发送即代表用户确认，平台不担责（UI 明示）。
- **隐私**：上下文脱敏、敏感信息不出域、用户可清除历史。
- **前置动作**：上线前走法务 + 安全评审。

---

## 8. 跨平台策略（降本关键）

| 方案 | 说明 | 适用 |
|------|------|------|
| 原生聊天 + WebView AI 面板（推荐） | 双端原生壳承载同一套 H5 面板，复用现有前端栈 | 团队有原生能力 |
| 全量 H5 + Capacitor 壳 | 一套 Web 包双端分发，进一步降本 | 原生薄弱 / 快速验证 |

视觉与交互组件统一，避免双端体验分裂。

---

## 9. 关键风险与缓解

| 风险 | 缓解 |
|------|------|
| 延迟影响体验 | 流式输出 + 打字时预检索 + 端侧骨架屏 |
| 推理成本 | 移动端服务端集中推理；可选小模型蒸馏；缓存高频话术 |
| RAG 召回质量 | 建立评测集 + 重排 + 人工抽检 |
| 合规风险 | 护栏前置 + 法务评审 + 免责明示 |
| 双端体验分裂 | 统一设计系统 + 共享 Web 组件 |

---

## 10. MVP 范围与排期（建议）

- **MVP（优先桌面端 H5 面板验证）**：
  - 桌面端 Web 面板 + 服务端编排 + RAG（FAQ + 话术库）+ 单 LLM + 采纳反馈。
- **Phase 2**：移动端 WebView 接入同一面板；画像风格向量；多候选 + 换一批。
- **Phase 3**：护栏强化、评测集、反馈回流优化。

**粗略估算**：前端 2~3 周、服务端编排 3~4 周、RAG 语料与评测 1~2 周、联调 1 周（MVP 约 6~8 周）。
